# ADR 0022: `bin/reactiph` CLI — compile, build, watch

- Status: accepted
- Date: 2026-09-23

## Context

Part 8, the last unstarted build-order part: "CLI/dev tooling (watch mode,
production build) + docs." The docs half is now substantially covered by
the separate `reactiph-docs` site (built earlier this session). What's
left is a real `bin/reactiph` executable — named but never built since
Part 1's original architecture sketch.

Two real, un-invented gaps motivate this beyond "the plan says so":
`Component\ComponentDiscovery::registerDirectory()` (ADR 0020) is a
deliberately uncached, request-time filesystem scan; and ADR 0021 named,
then explicitly deferred, "pre-transpiling component JS into a real
static file Vite could bundle" as separate scope needing "any CLI/build
tooling at all" first. Both point at the same missing piece: nothing in
this framework can turn a directory of components into static files
ahead of time.

## Decision

**Three subcommands, no config file, no console framework dependency.**

- `reactiph compile <ComponentClass>` — compiles one already-autoloadable
  component's template and transpiles its methods, printing the resulting
  JS to stdout. A fast single-component check while authoring one, and a
  CI-friendly way to catch a real `ReactiphException` (a template parse
  error, an unsupported PHP construct) before it ships.
- `reactiph build <source-dir> <output-dir>` — discovers every component
  under `<source-dir>` (via `ComponentDiscovery::classesInDirectory()`, a
  new public method exposing the same scan `registerDirectory()` already
  ran, now as data instead of a `ComponentRegistry` side effect) and
  transpiles each into its own static `<ShortClassName>.js` file, plus a
  `manifest.json` mapping each component's fully-qualified class name to
  its output file and a content hash. **This is the concrete piece ADR
  0021 deferred** — any host (a future Vite integration, `wordpress-bridge`,
  `taw-bridge`) now has a real static file and manifest to point at
  instead of transpiling at request time, without this package needing to
  know anything about that host's own asset pipeline. Wiring a specific
  bridge to prefer a pre-built file is still separate, real, undone work —
  this only produces the files.
- `reactiph watch <source-dir> <output-dir>` — reruns `build` once
  immediately, then again whenever a `.php` or `.reactiph.html` file
  under `<source-dir>` changes, detected by polling file mtimes (default
  every 500ms) rather than a native filesystem-events extension
  (`inotify`, `fswatch`, ...). Those aren't installed by default and
  differ per OS; a plain mtime scan needs nothing beyond core PHP and
  behaves identically everywhere this framework already runs. The
  tradeoff — a real change can take up to the poll interval to be
  noticed — is fine for a local dev loop.

**No config file** (a `reactiph.json` naming source/output directories,
included/excluded paths, etc.). All three commands take their
directory/class arguments directly on the command line. Nothing in this
framework yet has more than one plausible source directory or output
target, so a config format would be designed against a hypothetical need,
not a real one — revisit if that changes.

**Hand-rolled argv parsing**, not `symfony/console` or similar. Three
subcommands, each taking one or two positional arguments, don't need
option parsing, sub-sub-commands, or generated help text — the entire
dependency would exist to save writing a five-way `match` statement.

**`Application` writes to injected `$stdout`/`$stderr` streams** (default
`STDOUT`/`STDERR`), so most command-level behavior is testable without
shelling out — but `bin/reactiph` itself is still exercised as a real
process invocation in `tests/Cli/BinExecutableTest.php` (via `proc_open`),
since a resource-stream substitution doesn't prove the shebang, argv
wiring, or autoload-path detection in the actual executable work. Matches
how Part 4's Node parity tests and Part 6's `php -S` curl checks already
treat "crosses a real process boundary" as needing more than an in-process
unit test.

**A `ReactiphException` caught at the top of `Application::run()`**
becomes a structured stderr message (`code`, `message`, `hint`) and exit
code `1`, rather than a raw stack trace — ADR 0009's ethos applied to a
CLI instead of a caught-and-rendered web request. Anything that isn't a
`ReactiphException` is a genuine bug and is allowed to surface as an
ordinary uncaught-exception fatal error, not swallowed.

## Alternatives considered

- **A `reactiph.json` config file** naming components/source/output
  directories up front, so `build`/`watch` could run with no arguments.
  Rejected for now — real config-schema design work with no second real
  use case yet to design it against; three positional CLI arguments cover
  every real scenario this framework has today.
- **`symfony/console`** (or a similar micro-framework) for argument
  parsing and command structure. Rejected — the actual argument-parsing
  need (one or two positional paths/class names per subcommand) doesn't
  justify a new runtime dependency; revisit if flags/options genuinely
  proliferate later.
- **A native filesystem-events extension for `watch`** (`inotify` on
  Linux, `fswatch`/FSEvents on macOS). Rejected: not installed by default,
  platform-specific, and would need a fallback poller anyway for any
  environment without it — so the poller has to exist regardless, and a
  495ms-average-latency dev loop isn't worth the added complexity and
  platform branching to shave down further right now.
- **Caching `ComponentDiscovery`'s scan results** (e.g., `build` writing a
  manifest `ComponentDiscovery::registerDirectory()` could read back
  instead of re-scanning on every request) — real, related work, but a
  separate decision about how the *runtime* consumes a build artifact, not
  about what the CLI itself does. Left as an open thread.

## Consequences

- **`ComponentDiscovery::classesInDirectory()`** is now public API, not
  just an internal implementation detail of `registerDirectory()` — any
  future caller wanting the raw discovered-class list (not just
  `ComponentRegistry` side effects) has a supported way to get it.
- **`WatchCommand::watch()`'s baseline mtime snapshot is taken before the
  initial build runs, not after** — the more defensible ordering (nothing
  that happens *during* the initial build should be silently absorbed
  into "no change yet"), but also load-bearing for testability: a test
  simulating a file change from inside the `onBuild` callback would
  otherwise have that change folded into the very snapshot it's supposed
  to be compared against. See `docs/gotchas.md`.
- **No component method currently needs server-side-only behavior that
  `build`'s eager transpilation would leak** — `build` transpiles exactly
  the same `OwnMethods::of()` set `ComponentTranspiler` and `RpcHandler`
  already treat as client-transpiled/RPC-callable (ADR 0018's still-open
  "no server-only marking" thread). If that thread is ever resolved,
  `BuildCommand` needs to respect it too, not just `ComponentTranspiler`.
- **Static build output and request-time transpilation can now silently
  drift** if a host wires up the former without a process to keep it
  current — `build`/`watch` produce real files, but nothing invalidates a
  stale one if a component's PHP changes and nobody reruns `build`. Not a
  new problem this decision solves fully, just the first place it becomes
  possible to hit: previously, every render always re-transpiled live.
