# ADR 0020: Folder-based components — default template loading and directory-based discovery

- Status: accepted
- Date: 2026-09-23

## Context

Every component authored so far follows one pattern: extend `BaseComponent`,
implement `template()` returning an inline heredoc/nowdoc string, and
register a tag name by hand via `ComponentRegistry::register()` before any
template referencing it renders. The user asked for a second, MVC-ish way
of organizing components — a folder per component holding its class,
template, and (eventually) styles together — mirroring a pattern from
another project (TAW's MetaBlocks) they already find productive. Explicitly
scoped as *additive sugar*, not a replacement: every existing component,
all of which override `template()` inline, needed to keep working
unchanged.

Two real forks were identified and discussed with the user before
building anything:

1. How does a component's template stop needing to live in an inline
   PHP string? (Opt-in trait vs. no framework change at all vs. baking a
   default directly into `BaseComponent`.)
2. When does a folder-based component get registered — a request-time
   scan, deferred to Part 8's CLI, or a Composer-autoload/marker-interface
   scheme?

## Decision

**`BaseComponent::template()` is no longer abstract.** It gets a default
implementation: a component that doesn't override it has its markup loaded
from a sibling file named `{ShortClassName}.reactiph.html`, resolved via
reflection on the component's own class file path (`dirname((new
ReflectionClass($this))->getFileName())`) — never the working directory
`template()` happens to be *called* from, which for a cached, per-class
shared render closure (ADR — see `BaseComponent`'s own docblock) could be
any instance's own directory, not necessarily the component's. A component
that still overrides `template()` is completely unaffected; this is
additive, not a behavior change for existing code — confirmed by the full
existing test suite passing unmodified (every current component already
overrides `template()`).

The filename uses the class's own **short name**, not a fixed
`template.html`, so multiple components can share one flat directory
without colliding, and a custom `.reactiph.html` extension (not bare
`.html`) keeps a Reactiph template file unambiguous from an unrelated
`.html` file that might live in the same folder for some other reason. A
component with neither an override nor a matching file throws a new,
`ReactiphException`-compliant `MissingTemplateFileException` (ADR 0009's
convention), naming the exact path it looked for and how to fix it.

**`Component\ComponentDiscovery::registerDirectory()`** auto-registers
every component found under a directory, tagged by its own short class
name — no `ComponentRegistry::register()` call needed per component.
Discovery statically parses each `.php` file with `nikic/php-parser`
(already a core dependency) to learn its declared class name **without
including or evaluating the file** — arbitrary code in a scanned directory
never executes just because discovery walked past it. Only once a class
name is known does discovery lean on `class_exists()` to actually load it,
through the ordinary Composer autoloader — meaning a discovered class must
resolve through normal PSR-4 conventions; a class whose file doesn't sit
where its own namespace expects simply won't autoload, and is silently
skipped, the same as it would be anywhere else in the application. An
abstract `BaseComponent` subclass found this way is also skipped (nothing
to instantiate).

**Discovery is a request-time scan, run fresh on every call** — no
caching, no manifest. This is a deliberate, acknowledged cost, not an
oversight: simple and always correct for the framework's current maturity,
explicitly deferred to revisit (a cached manifest generated by a build
step) as natural follow-on work for Part 8's CLI/dev tooling, not
attempted here.

**Styles are explicitly out of scope.** A folder-based component's
eventual stylesheet has nowhere to be served from yet — there is no asset
pipeline anywhere in `packages/runtime-js`, the same gap already blocking
a Gutenberg block (ADR 0019). Rather than half-build a bundler as a side
effect of this decision, a `style.css` sitting in a component's folder is,
for now, just an inert file the framework does nothing with.

**Terminology: "components," not "blocks."** Reactiph's own roadmap
already plans an actual WordPress Gutenberg *block* integration (ADR
0004/0019) — reusing "block" for this unrelated folder convention would
collide with that later, real feature. This ADR and the code it describes
consistently say "folder-based component," never "block."

## Alternatives considered

- **No framework change — pure convention.** An author writes
  `return file_get_contents(__DIR__ . '/template.html');` inside their own
  `template()` override, with zero new framework surface. Rejected: this
  works today with no code changes at all, but doesn't remove any of the
  boilerplate the user actually wanted removed, and every author would
  reinvent the same few lines slightly differently.
- **An opt-in trait instead of a `BaseComponent` default.** A
  `LoadsTemplateFromFile` trait a component could `use` to gain the
  sibling-file lookup, leaving `template()` abstract for everyone else.
  Not chosen — the user picked baking the default into `BaseComponent`
  directly, accepting that this changes the base contract (`template()`
  no longer forces every subclass to implement it) for existing and future
  components alike.
- **Composer-autoload/marker-interface discovery**
  (`get_declared_classes()` after normal autoloading, filtered by an
  interface or attribute). Not chosen — generally more fragile and slower
  than a direct directory scan, and still needs something to have already
  triggered autoloading of every candidate class first, which a directory
  scan doesn't require.
- **A cached discovery manifest, built now.** Rejected for this pass:
  caching implies invalidation (a new component added mid-request-cycle,
  a file deleted) that's really a build-tooling concern, cleanly deferred
  to Part 8 rather than designed under this decision's narrower scope.

## Consequences

- `BaseComponent` can no longer be relied on to force every subclass to
  declare `template()` — a component that forgets to override it and has
  no matching template file now fails at **render time** with
  `MissingTemplateFileException`, not at class-definition time the way a
  genuinely unimplemented abstract method would have. This trade-off was
  accepted as part of choosing to bake the default in directly rather than
  keep it opt-in.
- `ComponentDiscovery` walks a whole directory tree and parses every
  `.php` file under it on every call — real, repeated cost for a directory
  with many files, not yet mitigated by any cache. Acceptable for now;
  tracked in `docs/STATUS.md` as a Part 8 follow-on, not silently ignored.
- A folder-based component's styles remain entirely unaddressed — this
  ADR deliberately does not attempt to solve asset serving for them.
- `examples/folder-components.php` and `examples/folder-based/` demonstrate
  both halves together end to end: `Greeting` never overrides `template()`
  (loads `Greeting.reactiph.html` from its own folder) and is never
  manually registered (found by `ComponentDiscovery::registerDirectory()`),
  yet resolves correctly as `<Greeting />` from a parent template. Required
  adding a new PSR-4 autoload-dev mapping
  (`ReactiphExamples\ => examples/folder-based/`) so discovery has a real,
  autoloadable class to find — a plain `require` would have demonstrated
  template loading but not genuine discovery.
